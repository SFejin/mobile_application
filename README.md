# WORK SAFE — 개발용 Android 베이스 앱

실제 작업자 계정으로 로그인하고, 휴대폰 낙상 감지에 따른 자동 SOS와 BLE 비콘 수신·송신,
Galaxy Watch의 측정 요약 수신을 사용하는 개발용 Android 앱입니다.
## 작업자 로그인

### 개발 중 서버 없이 시작하기

**debug 빌드**에서 로그인 화면에 **작업자 ID `1024` / 비밀번호 `0000`**을 입력하면
서버 인증 요청 없이 홈으로 이동합니다. Android Studio의 기본 `app` 실행 또는
`./gradlew :app:assembleDebug`로 만든 APK에서 사용할 수 있습니다.

- 홈과 설정 화면에 **개발 모드 · 서버 연결 없음**을 표시합니다.
- 휴대폰 센서, BLE 비콘, 워치 데이터 수신을 실제 기기에서 테스트할 수 있습니다. 각 기능의 기기 지원·권한·페어링 조건은 그대로 필요합니다.
- 워치 데이터를 받을 때는 개발 계정으로 진입한 다음 워치 측정을 새로 시작하세요.
- 낙상 감지 시 20초 알람과 취소 흐름은 **SOS 연습**으로 동작하고 서버 이벤트를 전송하지 않습니다.
- 개발 세션에는 서버 주소와 토큰이 없습니다. 프로필 변경은 메모리에만 반영되며, 비밀번호 변경과 탈퇴는 사용할 수 없습니다. 로그아웃도 서버 요청 없이 처리합니다.
- 개발 세션은 메모리에만 유지되므로 앱 프로세스 종료 후에는 다시 입력해야 합니다.
- 이 조합 이외의 계정은 기존 서버 인증을 사용합니다. 비밀번호는 앞뒤 공백까지 정확히 일치해야 합니다.
- **release 빌드에서는 이 예외가 비활성화**되어 `1024` / `0000`도 일반 서버 인증을 거쳐야 합니다.

### 사용 방법

1. 로그인 화면에서 **서버 주소**와 관리자 웹에서 발급받은 **작업자 ID와 비밀번호**를 입력합니다. 앱 자체 회원가입은 없으며, 개발 계정은 서버에 등록된 계정이 아닙니다.
2. 서버 인증에 성공하면 홈으로 이동하고 낙상 감시를 시작합니다. 감시 서비스 시작에 실패하면 세션을 해제하고 오류를 표시합니다.
3. 홈의 **작업자 ID**를 확인합니다. 자동 SOS는 이 작업자 계정의 인증 세션을 함께 사용하므로 별도 서버 로그인이 필요하지 않습니다.
4. 작업을 마치면 로그아웃합니다. 로컬 세션과 낙상·BLE 감시를 종료하고 서버에 토큰 폐기를 요청합니다.

기본 서버 주소는 `http://34.22.75.168:8081`이며
로그인 화면에서 변경할 수 있습니다. 실제 로그인이 완료된 서버 주소를 다음 로그인 화면에 사용합니다.
현재 기본 주소는 HTTP입니다. 인증 정보를 암호화해 전송하려면 서버 HTTPS 설정과 앱의 서버 주소 변경이 필요합니다.

작업자 ID는 양의 정수여야 합니다. 비밀번호 앞뒤 공백은 임의로 제거하지 않습니다.
로그인 요청 중에는 입력과 버튼을 잠그고, 실패하면 오류를 표시한 뒤 다시 입력할 수 있게 합니다.
이름은 로그인 응답에 없고 프로필 조회 GET API도 연결되어 있지 않아 서버에서 받은 이름처럼 표시하지 않습니다.

### 인증 API와 세션

- `POST /api/worker/auth/login`에 JSON `workerId`(숫자), `password`를 전송합니다.
- HTTP 200 응답의 `accessToken`, `tokenType: Bearer`, 미래 시각의 `expiresAt`을 검증한 뒤 세션을 생성합니다.
- 잘못된 비밀번호나 작업자 인증이 불가능한 계정은 로그인할 수 없습니다.
- 비밀번호와 토큰은 디스크에 저장하지 않습니다. 같은 프로세스의 화면 회전에는 세션을 유지하지만, 프로세스 종료 후에는 다시 로그인해야 합니다.
- 토큰 만료 또는 SOS 전송의 HTTP 401 응답을 확인하면 진행 중인 SOS 처리가 끝난 후 다시 로그인을 요구합니다.
- 로그아웃 시 `POST /api/worker/auth/logout`으로 토큰 폐기를 요청합니다. 오프라인에서는 서버 토큰 폐기가 보장되지 않습니다.
- 개인 정보 수정은 `PATCH /api/worker/me`의 응답이 현재 작업자와 일치할 때만 반영합니다. 비밀번호 변경은 `PATCH /api/worker/me/password`의 HTTP 204를 확인한 뒤 세션을 종료하며, 새 비밀번호로 다시 로그인해야 합니다.
- SOS 처리 중에는 로그아웃·비밀번호 변경·회원 탈퇴를 시작할 수 없습니다.

### 회원 탈퇴

설정 메뉴 → **회원 탈퇴** → 현재 비밀번호 입력 → **회원 탈퇴** → 최종 확인창의 **탈퇴** 순서로 진행합니다.
`DELETE /api/worker/me`에 현재 세션의 Bearer 토큰과 `{"currentPassword":"입력한 비밀번호"}`를 전송합니다.
HTTP 204 응답을 확인한 경우에만 탈퇴 완료를 표시하고 세션·낙상·BLE 감시를 종료합니다.
HTTP 401은 비밀번호 오류와 인증 만료 가능성을 함께 안내하며, 통신 오류나 응답 유실은 완료로 처리하거나 자동 재전송하지 않습니다.
SOS 처리 중에는 탈퇴를 시작하지 않으며, 탈퇴 요청 중에는 중복 요청과 화면 이동을 제한합니다.
입력한 비밀번호는 저장하거나 로그에 남기지 않습니다.

### 로그인 확인 방법

실제 발급 계정 로그인 → 홈 작업자 ID 확인 → 로그아웃 → 잘못된 비밀번호 거절 순서로 확인합니다.
`SosServerTest`는 로컬 모의 HTTP 서버로 로그인 요청 필드, 인증 거절, 잘못된 응답·만료·토큰 타입,
SOS의 동일 토큰 전달, HTTP 401 이후 세션 무효화와 로그아웃 헤더를 검사합니다.
모의 서버 테스트 성공은 실제 배포 서버의 로그인 성공을 의미하지 않습니다. 실제 계정과 서버에서 별도로 확인해야 합니다.

## 낙상 기반 자동 SOS

### 사용 방법

1. 실제 작업자 계정으로 로그인하고 홈의 작업자 ID와 낙상 감시 상태를 확인합니다.
2. 휴대폰 센서에서 낙상이 감지되면 **20초** 동안 알람·진동과 취소 안내를 표시합니다.
3. 도움이 필요하지 않다면 전송 시작 전에 앱 또는 알림의 **괜찮아요 · 취소**를 누릅니다.
4. 취소하지 않으면 로그인한 계정으로 `FALL_DETECTED` 이벤트 전송을 시도합니다. 서버의 정상 접수를 확인한 경우 이벤트 번호를 표시합니다.

자동 SOS는 휴대폰의 가속도계·자이로를 사용하는 낙상 감지에 연결되어 있습니다.
워치 심박수·온도를 수신했다고 생체 이상 SOS를 발생시키지는 않습니다.
대기 중의 중복 낙상 감지는 타이머를 연장하거나 전송 계정을 바꾸지 않습니다.
전송이 시작된 뒤에는 취소할 수 없으며, 종료·취소 후 **30초** 동안 반복 시작을 억제합니다.

### 전송 API와 결과

- `POST /api/worker/events`에 `Authorization: Bearer <accessToken>`을 사용합니다.
- 요청 본문은 `time`(낙상 시각의 ISO-8601 UTC 문자열), `eventType: FALL_DETECTED`, `alertSender: ANDROID_AUTO_SOS`입니다.
- 작업자는 본문의 작업자 ID가 아니라 인증 토큰으로 식별됩니다. 낙상 당시의 인증 세션을 사용합니다.
- HTTP 201과 응답의 작업자·이벤트 종류를 확인한 뒤에만 접수 완료로 표시합니다.
- 관리자 웹의 기존 낙상 이벤트 목록에서 확인하는 구조입니다. 별도 `AUTO_SOS` 이벤트 종류나 관리자 푸시·소리 알림을 추가한 것은 아닙니다.
- 인증 만료·통신 끊김·서버 오류는 실패 또는 접수 확인 필요로 표시합니다. 응답이 유실되어도 서버에서는 이미 접수했을 수 있으므로 자동 재시도하지 않습니다. 관리자 화면에서 접수 여부를 확인해야 합니다.

### 백그라운드 동작과 중단

- 서비스가 감지·대기·전송을 담당하므로 화면 회전이나 앱 화면 이동에 타이머가 종속되지 않습니다.
- Android 알림 권한이 꺼져 있으면 백그라운드 취소 알림이 표시되지 않습니다. 알림을 허용하고, 소리·진동은 기기 설정 및 하드웨어 상태를 확인하세요.
- 최근 SOS 결과는 로컬에 저장합니다. 대기 중 프로세스가 종료되면 다음 실행 시 중단/미전송으로, 전송 중 종료되면 접수 확인 필요로 표시합니다.
- 재부팅·강제 종료 후 자동 전송 복구는 제공하지 않습니다. 프로세스 종료 후에는 다시 로그인해야 합니다.

### 자동 검사와 실기기 확인

프로젝트 루트에서 다음 명령으로 단위 테스트, 앱·기기 테스트 APK 빌드와 Lint를 실행합니다.

```powershell
.\gradlew.bat --no-daemon :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug
```

`SosStateMachineTest`와 `SosServerTest`는 취소·대기시간·중복 감지·오래된 알림의 취소 요청·전송 후 취소 차단,
프로세스 종료 복구, HTTP 인증/이벤트 형식, HTTP 401/500·응답 유실·응답 불일치·만료를 검사합니다.
HTTP 테스트는 로컬 모의 서버를 사용합니다.

앱과 androidTest APK를 테스트 기기에 설치한 뒤 기기 통합 검사를 실행할 수 있습니다.

```powershell
adb shell am instrument -w com.example.safetymonitor.test/com.example.safetymonitor.BackgroundMonitoringTestRunner
```

기기 통합 검사는 테스트용 인증 세션·로그아웃·알람 연습·화면 잠금을 수행하므로 실제 작업 중인 기기에서 실행하지 마세요.
SOS 연습은 실제 이벤트를 전송하지 않지만, 연습 중 발생한 낙상 감지는 기존 대기에 합쳐집니다.
실제 화면·소리·진동·잠금 화면 취소와 실제 계정의 관리자 웹 수신은 별도 실기기 검증이 필요합니다.

## 빌드와 실행

- JDK 17 또는 21, Android SDK Platform 35가 필요합니다.
- Gradle 8.9 Wrapper가 포함되어 있습니다. 최초 실행에는 의존성 다운로드가 필요합니다.
- Android Studio에서 저장소 루트를 열고 Gradle JDK를 17/21로 선택한 뒤 `app`을 실행합니다.
  JBR/JDK 25는 이 Gradle 버전과 맞지 않으므로 사용하지 않습니다.

macOS 설정:

```sh
export JAVA_HOME="$HOME/Library/Caches/worksafe-dev/jdk-21.0.13+9/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"
./gradlew --no-daemon :app:testDebugUnitTest :app:assembleDebug :app:lintDebug
```

다른 환경에서는 `JAVA_HOME`과 SDK 경로를 설치 위치에 맞게 지정합니다.
생성되는 APK: `app/build/outputs/apk/debug/app-debug.apk`

에뮬레이터 또는 Android 8.0 이상 기기를 연결한 뒤:

```sh
"$ANDROID_HOME/platform-tools/adb" install -r app/build/outputs/apk/debug/app-debug.apk
"$ANDROID_HOME/platform-tools/adb" shell am start -W -n com.example.safetymonitor/.MainActivity
```

여러 기기가 연결되어 있으면 adb 명령에 `-s <기기 시리얼>`을 추가합니다.

## 계정과 상태 수명

- 실제 서버 연결에는 관리자 웹에서 발급한 작업자 계정을 사용합니다. debug 빌드의 `1024` / `0000`은 서버에 연결하지 않는 로컬 개발 계정입니다.
- 비밀번호와 토큰은 디스크에 저장하지 않습니다. 프로세스 종료 후 다시 로그인합니다.
- 로그아웃하면 로컬 인증과 감시 서비스를 종료하고 서버 토큰 폐기를 요청합니다.
- 토큰 만료 또는 SOS 전송의 HTTP 401 응답을 확인하면 다시 로그인을 요구합니다.
- 개인 정보 수정은 임시 화면 데이터이며 서버에 저장되지 않습니다.
- 비밀번호 재발급은 관리자에게 요청합니다. 회원 탈퇴는 앱에서 현재 비밀번호 확인 후 서버에 요청합니다.
- 화면 테마는 SharedPreferences에 저장합니다.

## BLE 거리·2D 위치 데모

동일 앱의 송신 모드가 내보내는 전용 UUID·8바이트 Service Data만 처리합니다.
임의 BLE 기기나 상용 iBeacon/Eddystone을 자동으로 거리 측정하는 기능은 아닙니다.

### 수신 — 기본 모드

- 로그인 후 기본 역할은 수신입니다. 권한이 없으면 홈에서 차단 사유와 사용자 조작을 표시하며, 권한을 임의로 허용하거나 반복 요청하지 않습니다.
- Android 12 이상은 주변 기기 검색과 정확한 위치 권한, Android 8~11은 위치 권한이 필요합니다. 위치 서비스와 Bluetooth도 켜져 있어야 합니다. 백그라운드 위치의 ‘항상 허용’은 요구하지 않습니다.
- 홈에 실제 비콘 ID·송신 좌표·RSSI 중앙값·추정 거리·최근 관측을 표시합니다. 최근 최대 5개 RSSI의 중앙값과 `d = 10^((A - RSSI) / (10 × 2))`를 사용합니다. `A`는 **1m 기준 RSSI**이며 송신 출력 설정이 아닙니다.
- 최신·유효·고유 ID의 사용 가능한 비콘 수에 따라 표시를 바꿉니다.
  - **0개 — 위치 미확정:** 이전 위치 점이나 거리 원을 남기지 않습니다.
  - **1개 — 비콘 거리 참고:** 고정 비콘의 ID·추정 거리와 참고 원을 표시합니다. 작업자 좌표나 사용자 점은 만들지 않습니다.
  - **2개 — 가중 참고 위치:** `1/d` 역거리 가중 비콘 중심점을 마름모로 표시합니다. 두 거리 원의 교차해나 유일하게 측정된 실제 위치가 아닙니다.
  - **3개 이상 — 2D 근사 위치:** 기존 삼변측량 솔버가 성공하면 근사 위치 점을 표시합니다. 일직선 배치 등으로 실패하면 원래 실패 사유와 함께 가중 참고 위치로 낮춥니다.
- 좌표는 송신기에 설정한 공통 기준의 미터 단위이며 GPS·지도 좌표가 아닙니다. 일반 BLE RSSI만으로 방향은 알 수 없습니다. 거리 원은 실제 위치의 보장 경계나 통계적 신뢰구간이 아닙니다.
- 표본의 나이가 5초를 초과하면 만료합니다. 동일 ID의 좌표·기준 RSSI가 충돌하면 해당 비콘만 계산에서 제외합니다. 남은 사용 가능한 비콘 수에 맞춰 표시를 낮추며 이전 좌표를 현재 위치인 것처럼 유지하지 않습니다.
- 화면의 일반 주의 문구는 `장애물과 환경에 따라 오차가 발생할 수 있습니다.` 한 줄로 표시합니다. 권한 차단·실제 오류·잘못된 입력 안내는 유지합니다.

### 숨김 송신 모드

1. 로그인한 홈의 `WORK SAFE` 제목을 **3초 안에 7번** 누르면 송신 설정을 엽니다. 설정 진입이나 값 저장만으로 송신하지 않으며 기존 수신을 유지합니다.
2. 기본 화면에서 송신기 ID `1~65535`와 1m 기준 RSSI를 설정합니다. 기준 RSSI는 `-127~-1dBm`, 기본값은 보정되지 않은 예시 `-59dBm`입니다. 설치 X/Y는 **고급 설정**을 펼칠 때만 보입니다. 좌표 범위는 `-327.68~327.67m`이며 cm 단위로 반올림해 저장합니다.
3. 명시적으로 송신을 시작하고 필요한 광고 권한을 허용합니다. 광고 시작 콜백이 성공해야 송신 중으로 표시합니다. 송수신은 동시에 실행하지 않습니다.
4. 송신 중지 또는 수신 복귀를 선택할 수 있습니다. 설정만 저장하고 송신하지 않는 상태도 허용합니다. 송신 설정은 저장되지만 실행 여부는 저장하지 않으므로 새 프로세스·재부팅 뒤 자동 송신하지 않습니다.

고급 설정을 접어도 저장값과 입력 중인 좌표는 유지됩니다. 좌표가 잘못되면 오류와 필드가 보이도록 접기를 막습니다. 새 설정의 기본 좌표 `(0,0)`은 원점이지 ‘미사용’ 표시는 아닙니다. 거리 측정만 사용할 때는 그대로 두어도 되지만, 2D 위치 계산에는 비콘별 공통 기준 배치 좌표가 필요합니다.

거리 시연은 수신기 1대와 광고를 지원하는 송신기 1대로 시작할 수 있습니다. 가중 참고 위치에는 송신기 2대, 삼변측량 근사 위치에는 서로 다른 ID와 적절한 배치의 송신기 3대 이상이 필요합니다. 비콘 수가 늘어도 정확도 향상이 보장되지는 않습니다.
예를 들어 ID 1을 `(0, 0)m`, ID 2를 `(4, 0)m`, ID 3을 `(0, 3)m`에 고정하고 실제 배치도 맞춥니다.
반사·벽·사람·기기 방향에 따라 RSSI와 위치가 크게 흔들릴 수 있습니다. 1m 기준 RSSI도 실제 환경에 맞춰 보정해야 합니다.

### 화면 꺼짐·중지·정보 범위

- 화면이 보일 때 시작한 BLE 포그라운드 서비스가 앱 전환·화면 꺼짐 뒤에도 동작하도록 구성했습니다. 수신은 `location|connectedDevice`, 송신은 `connectedDevice`를 사용하며 기존 낙상 서비스와 분리됩니다.
- BLE 알림의 중지 또는 앱의 중지는 BLE만 멈춥니다. 로그아웃·탈퇴는 BLE도 종료합니다. 명시적 중지 뒤 앱을 다시 보는 것만으로 자동 재시작하지 않습니다.
- 권한 거절·지원 불가·초기 Bluetooth/위치 꺼짐은 차단 상태와 조치로 안내합니다. 설정을 해결한 뒤 앱으로 돌아와 필요한 시작 동작을 수행합니다. 강제 종료·재부팅·시스템의 서비스 종료 뒤 무인 복원을 보장하지 않습니다.
- 알림 권한을 거절하면 알림 표시가 제한됩니다. 포그라운드 서비스가 유지돼도 OS가 스캔 주기를 낮출 수 있으므로 화면 꺼짐 중 고정 주기의 위치 갱신은 보장하지 않습니다. 각 비콘의 새 표본이 5초를 초과해 없으면 해당 비콘이 만료되어 표시 단계가 낮아지거나 위치 미확정이 됩니다. 실제 수신 지속과 배터리 영향은 OS·기기별로 실측해야 하며, 절전 예외나 권한을 강제로 설정하지 않습니다.
- 광고에는 버전·ID·좌표·기준 RSSI만 평문으로 들어갑니다. 주변에서 읽거나 위조할 수 있으므로 민감한 실제 위치·식별 정보를 넣지 마세요. GPS·계정 정보·위치 이력을 수집하거나 서버에 보내지 않습니다.

### BLE 검증 범위

- JVM 단위 테스트 **11개(추정기 7개·프로토콜 4개)**에서 패킷 경계/오류, RSSI 중앙값·만료·순서, ID 충돌 복구, 0→1→2→3→2→1→0 전환, 역거리 가중값, 정상/퇴화 기하·영역 밖 해와 3개 이상 실패 시 사유를 보존한 가중 전환을 확인했습니다. 이는 실제 송신기 3대의 무선 검증이 아닙니다.
- 통합 `testDebugUnitTest`, `assembleDebug`, `lintDebug`가 성공했습니다.
- Pixel_4a 에뮬레이터(API 37)에서 권한 미허용 상태, 7탭 진입 후 송신 대기, 송신 시작 권한 거절과 홈의 차단 상태, 음수·소수 좌표 입력, 앱 내부 라이트·다크 전환을 실제 화면으로 확인했습니다. 이 검증에서는 BLE 권한을 허용하지 않았고 스캔·광고 성공을 확인한 것은 아닙니다.
- 같은 에뮬레이터에서 Android 설정 UI로 승인된 권한만 허용한 뒤 실제 스캔 시작과 광고 성공 콜백(`status=0`), 송수신 배타 전환, 앱의 송신 중지·알림의 수신 중지, 중지 후 재진입, 새 프로세스의 기본 수신/자동 송신 없음도 확인했습니다.
- 화면을 6분 이상 끈 추가 시험에서 수신 스캐너 등록·서비스는 유지됐지만, 스캔 시작 약 5분 뒤 실제 모드가 `LOW_LATENCY → LOW_POWER`, 이후 `SCREEN_OFF`로 낮아진 것을 Bluetooth 로그로 확인했습니다. 스캔 중단이나 `OPPORTUNISTIC` 전환은 아니었습니다. 이 에뮬레이터에서 관측한 `SCREEN_OFF` 스캔 간격은 약 10.24초로 5초 표본 만료보다 길어, 위치가 계속 확정된다고 보장할 수 없습니다. API 37 이미지의 결과이며 S23U에서도 동일한 제한 시간·주기라고 단정하지 않습니다.
- 필터가 있는 스캔의 시간 초과 시 저전력 전환은 [고정 리비전의 AOSP `ScanManager`](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/c77db469de80f86660bc053bec4dee0c5d4b947c/android/app/src/com/android/bluetooth/le_scan/ScanManager.java)과 대조했습니다. 서비스 생존·스캐너 등록·요청한 `LOW_LATENCY` 모드만으로 실제 무선 수신 빈도를 입증할 수 없습니다.
- 위 에뮬레이터 시험에서는 화면 꺼짐 중 광고가 25초 동안 유지됐습니다. 당시 실제 송신기가 없어 RSSI 콜백·거리·위치 갱신을 확인한 것은 아닙니다. 에뮬레이터의 서비스 생존이나 광고 성공 콜백을 실물 RF 송수신 증거로 해석하지 않습니다.
- 초기 단계형 APK에서 S23 Ultra SM-S918N(API 36)를 수신기로, Xperia 1 J9110(API 30)의 ID 1 `(0,0)m`와 Tab S10 Ultra SM-X926N(API 36)의 ID 3 `(0,3)m`를 실제 송신기로 사용했습니다. 두 송신기의 예시 기준 RSSI는 `-59dBm`입니다. 수신 없음 → 1개 거리 참고 → 2개 가중 참고 위치 → 송신기 1대 중지 뒤 1개 → 나머지 중지 뒤 미확정 전환을 확인했습니다. 중지 후 화면 캡처는 약 9초 뒤이므로 정확한 만료 지연을 측정한 것은 아닙니다.
- 지도 표시 개선 단계에서 검증한 APK의 SHA256은 `4767449fca8bf0ce5558f409687544deca25b1f0a5b10868650e5fe2b04b619e`입니다. 이 APK의 빌드·lint 및 승인된 세 기기의 데이터 보존 설치가 성공했습니다. 실제 1비콘 거리 참고와 2비콘 가중 참고 위치, 방향 미확정 안내 및 ID/좌표 목록을 확인했습니다.
- 지도 내 마커 글자를 기존 비콘 목록으로 분리하고 윤곽 마름모를 사용한 뒤, 실제 2비콘 화면에서 가까운 앵커 중심·마름모·카드·고정 범례를 식별할 수 있었고 글자 겹침이 없었습니다. 이 단계의 캡처는 원이 경계를 가로지르는 장면이 아니므로, 이전 APK에서 확인한 경계 clip 증거와 구분합니다. 시험 후 세 기기의 BLE를 정상 중지했고 기존 낙상 서비스만 남았으며, 실행한 호스트 헬퍼는 없습니다.
- 이후 안내 문구·고급 좌표 설정을 통합한 최신 APK `7bdbadc4774cb9eb4668b96dfc5d894c4a72e71ac60b1f5ce6a868a9fcc2952b`의 빌드와 S23U 설치가 성공했습니다. 실제 화면에서 한 줄 안내, 7탭 송신 설정 진입, 기본 좌표 숨김, 펼치기·접기 후 비저장 값 보존, 잘못된 X 입력 시 오류 노출과 접기·저장·시작 비활성화를 확인했습니다. 기존 저장 좌표는 유지했고 TX는 시작하지 않았습니다. 자동 시작된 RX는 정상 중지해 낙상 서비스만 남겼습니다. 이 UI 변경 검증에서 RF·단위 테스트·lint·송신 중 분기는 재시험하지 않았습니다.
- 초기 단계형 APK의 약 **30.5초 화면 꺼짐 요청 구간**에서 BLE와 낙상 포그라운드 서비스가 유지된 표본을 얻었습니다. 사용자 잠금 해제 후 재진입에서 1개 비콘 거리 표시를 확인했고, 같은 프로세스에서 수신 중지 → HOME → 재진입 뒤에도 중지·미확정 상태와 수신 시작 버튼이 유지됐습니다. 잠금 해제 지연이 있어 즉시 깨어난 순간이나 화면 꺼짐 중 연속 RF/위치 계산을 입증하지는 않습니다.
- 이전 APK의 별도 약 8분 실기기 화면 꺼짐 시험에서는 자체 스캐너의 프레임워크 콜백이 관측됐지만 5초 만료보다 긴 수신 간격도 있었습니다. 이를 현재 APK의 연속 추정·모든 비콘의 최신성 보장으로 해석하지 않습니다.
- 실제 송신기 3대의 2D 계산·실패 시 가중 표시, 실제 배치/이동 정확도, 화면 꺼짐 중 연속 위치 갱신은 미검증입니다. 순차 XML·스크린샷은 같은 snapshot이 아니므로 서로 결합해 정확한 가중 좌표 일치를 주장하지 않습니다. XZ Premium은 연결 문제로 검증에서 제외했습니다.

## 실시간 센서 화면 및 Android Studio 실행

- 프로젝트 루트(`settings.gradle.kts`가 있는 폴더)를 Android Studio에서 엽니다.
- Gradle JDK는 17 또는 21을 선택합니다. 현재 Gradle 8.9/Kotlin 2.0.20 구성에서 JDK 25는 사용하지 않습니다.
- Gradle Sync 후 `app` 실행 구성을 선택해 실행합니다. 관리자에게 발급받은 작업자 ID와 비밀번호로 로그인합니다.
- 로그인 후 기존 홈 화면의 가속도 센서 행에 가속도 합성값(m/s²)이 약 100ms 간격으로 표시됩니다. 자이로 센서는 내부 낙상 판정에 사용하며 별도 표시 영역은 추가하지 않습니다. 가속도는 중력을 포함하므로 정지 시 합성값은 약 9.81m/s²입니다.
- 낙상 판정은 가속도계의 자유낙하/충격, 자이로의 큰 회전, 두 센서의 3초 정지를 확인합니다. 한 센서가 없거나 등록에 실패하면 낙상 감지를 비활성화하고, 사용 가능한 센서 값은 계속 표시합니다.
- 두 센서 모두 새 값을 수신해야 판정하며, 한 센서 값이 500ms 이상 지연되면 진행 중인 판정을 초기화합니다.
- 로그인하면 알림을 표시하는 포그라운드 서비스에서 측정을 시작합니다. 다른 화면/앱으로 이동하거나 화면을 잠그거나 최근 앱에서 화면을 제거해도 측정을 계속합니다. 로그아웃 또는 회원 탈퇴 시 서비스·센서·알림을 종료합니다. 앱을 다시 열면 측정 세션과 최신 값이 연결됩니다. Android 13 이상에서는 측정 알림 권한을 요청하며 거부하더라도 측정은 계속됩니다. 기기 재부팅이나 시스템 설정에서 앱 강제 종료 후에는 앱을 다시 열어야 합니다. 낙상 이벤트는 자동 SOS 대기 후 로그인한 계정으로 서버에 전송합니다.

### 백그라운드 측정 검증

에뮬레이터에서 로그인, 홈 이동, 화면 잠금, Activity 작업 제거, 재진입, 로그아웃과 알림 정리를 확인하는 검증은 app/src/androidTest의 BackgroundMonitoringTestRunner에 있습니다. 앱과 androidTest APK를 설치한 뒤 다음 명령으로 실행합니다.

adb shell am instrument -w com.example.safetymonitor.test/com.example.safetymonitor.BackgroundMonitoringTestRunner

## 작업자 서버 API 통신 계층

`network/WorkerApiClient.kt`와 `WorkerApiModels.kt`는 작업자 API 호출을 위한 독립 통신 계층입니다. 서버 계약은 `mobileProgrammingTeam/server`의 기본 프로젝트만 있는 `main`이 아니라 [master의 고정 리비전 `42f2a75190db910e6fee29082494d927a4ef9e02`](https://github.com/mobileProgrammingTeam/server/tree/42f2a75190db910e6fee29082494d927a4ef9e02)을 기준으로 합니다. 현재 로그인과 자동 SOS는 `sos/SosServer.kt`를 사용하며 회원 탈퇴는 `WorkerApiClient.deleteAccount`를 사용합니다. 기존 `AlertSender`는 해당 실행 경로에 사용하지 않습니다.

| 메서드 | 경로 | 성공 | 요청 / 응답 DTO |
|---|---|---:|---|
| POST | `/api/worker/auth/login` | 200 | `WorkerLoginRequest` / `WorkerTokenResponse` |
| POST | `/api/worker/auth/logout` | 204 | 없음 / 없음 |
| POST | `/api/worker/events` | 201 | `WorkerEventRequest` / `WorkerEventInfo` |
| PATCH | `/api/worker/me` | 200 | `WorkerProfileUpdate` / `WorkerInfo` |
| PATCH | `/api/worker/me/password` | 204 | `WorkerPasswordChange` / 없음 |
| DELETE | `/api/worker/me` | 204 | `WorkerPasswordConfirmation` / 없음 |

호출자가 서버 루트 `baseUrl`을 제공합니다. 기본값은 HTTPS만 허용하며 로컬 개발 HTTP는 `allowInsecureHttp = true`로 명시적으로 선택해야 합니다. HTTP는 암호화되지 않으므로 실제 비밀번호나 토큰에 사용하지 마세요. 클라이언트는 무상태이며 로그인 외 보호 호출마다 호출자가 access token을 전달합니다. 토큰 저장·갱신·프로필 GET은 제공하지 않으며, 만료와 인증 실패에 대한 처리는 호출자가 담당합니다.

호출 예시는 코루틴 내부에서 실제 배포 환경의 `serverRoot`, `workerId`, `password`를 호출자가 제공하는 경우입니다.

```kotlin
val api = WorkerApiClient(baseUrl = serverRoot)
val session = api.login(WorkerLoginRequest(workerId, password))
val updated = api.updateProfile(session.accessToken, WorkerProfileUpdate(workerName = newName))
api.logout(session.accessToken)
```

HTTP 실패는 `WorkerApiException`의 상태 코드와 서버가 제공한 코드·메시지로 전달되며 통신 실패와 취소는 호출자에게 전파됩니다. 자동 리디렉션과 애플리케이션 수준 재시도는 없고, 본문은 UTF-8 고정 길이 스트리밍으로 전송합니다. 플랫폼의 연결 복구까지 완전히 막거나 서버가 요청을 정확히 한 번만 처리한다고 보장하지 않습니다. 타임아웃·취소 시 서버 처리 여부는 불확실할 수 있습니다.

이번 API 계층은 debug 빌드와 네트워크 없는 생성자·입력 검증·민감 문자열 마스킹 초기화 확인만 수행했습니다. Android JSON 런타임, 실제 HTTP/TLS 통신, 인증·서버 오류·취소·라이프사이클 및 실제 서버 계약 일치는 검증하지 않았습니다. 이 결과는 앱의 서버 연결이나 이벤트 전송 성공을 의미하지 않습니다.

## Galaxy Watch 연결

### 연결 준비

워치가 수집한 데이터를 Wear OS **Data Layer**로 휴대폰에 전달합니다.
페어링된 기기의 Bluetooth 연결을 사용하며 Wi-Fi·클라우드 경로도 사용할 수 있습니다.
별도 Bluetooth 소켓을 연결하거나 Bluetooth 전용 경로를 강제하는 구조는 아닙니다.
BLE 비콘 측위 기능과 워치 데이터 수신은 서로 다른 기능입니다.

| 항목 | 휴대폰 앱 | 워치 앱 |
|---|---|---|
| 프로젝트 / 모듈 | `mobile_application` / `app` | `WorkerSafetyStarter` / `wear` |
| applicationId | `com.example.safetymonitor` | `com.example.safetymonitor` |
| capability | `workersafety_phone` | `workersafety_watch` |
| 서명 | 두 APK의 서명 인증서가 같아야 함 | 휴대폰과 같은 인증서 사용 |

capability는 각 모듈의 `src/main/res/values/wear.xml` 안에 있는 `android_wear_capabilities` 배열에 선언합니다.
워치의 Kotlin 패키지명과 namespace는 휴대폰과 달라도 되지만 applicationId는 같아야 합니다.
워치 빌드에는 공식 Samsung Health Sensor SDK의 `samsung-health-sensor-api-1.4.1.aar`를
`WorkerSafetyStarter/wear/libs/`에 배치해야 합니다. 실제 센서 측정에는 지원 기기·센서 권한 및 삼성 SDK 실행 조건도 필요합니다.

같은 PC의 기본 debug 설정으로 두 앱을 빌드하면 일반적으로 같은 `~/.android/debug.keystore`를 사용합니다.
다른 PC에서 빌드한다면 동일한 개발용 키를 별도로 공유하고, 두 프로젝트의 빌드 명령에
`-PpairDebugKeystore=C:/private/team-debug.keystore`를 지정합니다.
이 옵션은 기본 debug 키 형식(`androiddebugkey` / `android`)을 사용하며 release에는 적용하지 않습니다.
키 파일은 저장소에 올리지 않고, release 빌드는 별도로 동일한 배포 서명을 설정합니다.

각 프로젝트 루트에서 서명을 확인합니다.

```powershell
# mobile_application 폴더
.\gradlew.bat :app:signingReport

# WorkerSafetyStarter 폴더
.\gradlew.bat :wear:signingReport
```

출력의 **debug SHA-256**이 같아야 합니다. 소스를 다시 빌드했다면 그때 생성한 두 APK를 함께 설치하세요.
이미 설치된 앱의 서명이 다르면 업데이트 설치가 거절될 수 있습니다.
이전 워치 앱의 applicationId가 다르면 별도 앱으로 설치될 수 있으므로 기존 앱의 측정을 종료하고 새 앱을 실행합니다.

### 연결 및 전송 순서

1. Galaxy Wearable 등 기기 설정에서 Android 휴대폰과 지원 Galaxy Watch를 페어링합니다.
2. 같은 applicationId와 서명으로 빌드한 두 앱을 각각 설치하고, 두 기기의 자동 날짜·시간을 켭니다.
3. 휴대폰 앱에서 실제 작업자 계정으로 로그인하고 **워치 연결 새로고침**을 누릅니다.
4. 로그인한 뒤 워치에서 측정을 시작합니다. 이미 측정 중이었다면 종료하고 다시 시작합니다.
5. 워치에 센서 값이 수집되면 연결 화면의 **지금 전송**을 누릅니다.
6. 휴대폰 홈의 연결 상태·평균 심박수·손목 피부온도·주변 온도·측정 구간 종료 시각이 갱신되는지 확인합니다.
7. 수신 확인을 지원하는 워치 앱에서는 전송 상태가 **휴대폰 수신 완료**로 바뀌는지도 확인합니다.
8. 휴대폰 앱을 백그라운드로 보낸 뒤 전송하고, 홈 복귀 시 최신 값이 표시되는지 확인합니다.
9. 연결을 끊었다가 복원한 뒤 최신 요약 갱신을 확인합니다. Bluetooth만 끄면 다른 경로로 통신할 수 있으므로 완전 단절 시험에서는 Wi-Fi 등도 고려합니다.

### 전달하는 데이터와 갱신 주기

워치는 **5분 또는 10분마다 측정 구간의 요약**을 보내며, **지금 전송**으로 현재 구간을 즉시 보낼 수 있습니다.
모바일의 **워치 연결 새로고침**은 연결 상태와 이미 전송된 최신 데이터를 다시 조회하는 버튼입니다.
워치의 센서를 새로 측정하도록 요청하거나 매초 실시간 스트리밍하는 기능은 아닙니다.

| 표시 항목 | 의미 |
|---|---|
| 평균 심박수 | 해당 측정 구간의 유효 심박수 평균, bpm |
| 손목 피부온도 | 해당 구간의 마지막 유효 피부온도, °C |
| 주변 온도 | 해당 구간의 마지막 유효 주변 온도, °C |
| 측정 구간 종료 | 워치가 전송한 측정 종료 시각 |
| 데이터 상태 | 전송 주기 + 2분을 넘으면 업데이트 지연 / 이전 측정값으로 표시 |

측정하지 못한 값은 0으로 만들지 않고 **측정값 없음**으로 표시합니다.
SpO₂는 현재 전송 항목이 없습니다. 수신한 생체값의 서버 업로드나 생체 이상 SOS는 연결되어 있지 않습니다.

### 수신 경로와 수신 확인

- 요약은 `/workersafety/summary` 경로의 DataItem으로 수신합니다.
- `WearableListenerService`가 백그라운드 데이터·연결 변경을 받고, ViewModel이 살아 있는 동안 15초마다 연결과 최신 데이터를 확인합니다. 홈 복귀와 새로고침 버튼에서도 조회합니다.
- 데이터에는 `window_start`, `timestamp`, `interval_minutes`, `has_hr`, `hr_avg`, `hr_count`, `has_skin`, `skin_c`, `skin_count`, `has_ambient`, `ambient_c`가 사용됩니다. `has_*`가 false인 측정값 필드는 없어야 합니다.
- 유효한 `summary_id`가 있으면 `/workersafety/summary/receipt`로 같은 ID와 수락/거절 결과를 회신합니다. ID가 없는 이전 형식은 회신 없이 처리하며, 잘못된 ID가 들어 있으면 해당 데이터를 거절합니다.
- **전송 등록됨 · 휴대폰 수신 대기**는 Data Layer에 전송을 등록했다는 의미입니다. **휴대폰 수신 완료**는 모바일이 해당 요약을 수락했다는 의미입니다. 휴대폰 화면의 값과 시각도 함께 확인합니다.

### 계정 구분과 연결이 안 될 때

- 로그인 시각 전에 시작된 측정 구간은 제외합니다. **휴대폰에 먼저 로그인한 뒤 워치 측정을 시작**해야 합니다.
- 로그인 중 처음 수신한 워치에 고정합니다. 다른 워치로 바뀌면 다시 로그인해야 하며, 여러 워치가 연결되어 있으면 한 대만 연결하도록 안내합니다.
- 타입·유효 플래그·수치 범위·개수·시각을 검증합니다. 직전 구간과 겹치는 새 요약은 거절하며, 같은 ID와 데이터의 최신 요약이 재도착하면 값과 시각을 유지한 채 다시 회신합니다.
- 현재 프로토콜에는 작업자/세션 ID가 없어 로그인 시간 경계와 워치 노드로 구분합니다. 공유 워치의 엄밀한 계정 결합에는 별도의 세션 ID 교환이 필요합니다.
- 최신 값은 로그인 세션과 같은 수명의 메모리에 보관합니다. 로그아웃·계정 변경 시 초기화하며, 이전 세션에서 시작된 수신·새로고침은 새 세션에 결과를 적용하지 않습니다. 프로세스 종료 후에는 다시 로그인·측정해야 합니다. 전체 측정 이력은 저장하지 않습니다.
- 미연결이면 페어링, 양쪽 앱 설치, applicationId·서명, capability와 Google Play 서비스를 확인합니다.
- 연결됐는데 값이 없으면 로그인 후 새 측정인지, 기기 시각이 맞는지, 센서 권한과 실제 센서 수집 상태를 확인합니다.
- 워치에 로그인 또는 새 측정이 필요하다는 안내가 뜨면 휴대폰 로그인 상태를 확인하고 워치 측정을 종료·재시작합니다.

### 워치 연결 검증 범위

`WatchSummaryTest`는 수신 형식, 센서 누락, 잘못된 형식·수치·미래 시각, 업데이트 지연 표시,
중복·역순·재연결, 다른 워치 차단과 로그인 경계를 검사합니다.
`WatchLinkProtocolTest`는 수신 확인 메시지 형식, 거절 사유, 잘못된 메시지와 늦게 도착한 수신 확인 처리를 검사합니다.
위 자동 SOS 절의 Gradle 명령에 이 모바일 단위 테스트도 포함됩니다.
실기기 페어링, Bluetooth 전송, 백그라운드 수신, 재연결과 삼성 SDK의 센서 측정 성공은 자동 테스트만으로 확인되지 않으므로 별도로 검증해야 합니다.
